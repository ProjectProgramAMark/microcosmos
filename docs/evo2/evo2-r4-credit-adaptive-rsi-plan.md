# Evo²-Ecosystem r4: Credit-Adaptive Heredity Under a Causally Valid Ecological Shock

Status: implementation-ready prospective plan

Date: 2026-07-13

Primary repositories: `microcosmos` and `ShinkaEvolve`
Prior evidence boundary: r1–r3 are complete, frozen, immutable negative or infrastructure results

## 1. Executive decision

Build one final, bounded r4 experiment whose purpose is to give recursive
self-improvement a fair opportunity to produce a real improvement without
expanding the project into a new simulator.

The r4 research question is:

> Can ShinkaEvolve discover an online, credit-responsive TensorNEAT heredity
> scheduler that improves recovery of embodied CPPN populations after a
> genuinely harmful ecological shock, relative to the scheduler from which the
> outer program lineage started?

The implementation keeps the complete r3 substrate:

- physically embodied filament organisms in Microcosmos;
- fixed-capacity, GPU-native JAX state;
- TensorNEAT CPPN controllers from the first organism onward;
- food-earned asynchronous birth, death, and slot reuse;
- finite resources, metabolism, lineages, and founder authentication;
- trusted fixed-shape TensorNEAT mutations;
- a bounded Shinka evolve block and executable verifier;
- stable-versus-punctuated outer-search arms;
- prospective manifests, hidden development and sealed partitions, and
  founder-first inference.

R4 changes only three scientific surfaces:

1. Replace the invalid tail-actuator injury with a prospectively qualified
   global actuation-cost shock. The shock must demonstrably hurt clone controls
   while leaving reproduction and adaptation possible.
2. Expand the trusted heredity menu from four coarse deterministic choices to
   six fixed choices containing conservative, standard, and exploratory
   parametric mutation scales.
3. Give the evolved scheduler bounded recent credit describing how offspring
   from each trusted operator fared. Shinka still writes only the selection
   rule; it cannot write mutation, physics, ecology, scoring, or hidden tests.

The scientific target is not “find a higher-scoring final swimmer.” The target
is a better program for producing future generations:

```text
Shinka program lineage improves make_offspring
                         ↓
make_offspring schedules trusted TensorNEAT heredity actions
                         ↓
offspring live, forage, reproduce, and die in Microcosmos
                         ↓
trusted code assigns recent credit to the action that made each offspring
                         ↓
the scheduler changes future heredity choices using that feedback
                         ↓
sealed recovery and ancestor–descendant adaptation test the improvement
```

This is bounded recursive program improvement: the outer system improves a
program that governs the inner system’s ability to generate adaptive
descendants. It is not unrestricted self-modification, open-ended evolution,
or a claim of abiogenesis.

## 2. Why r4 is necessary

### 2.1 What r3 established

R3 established that the difficult infrastructure is real and working:

- embodied CPPN populations reproduce and turn over in a shared fluid world;
- mutation occurs on food-earned asynchronous births rather than in a detached
  generational optimizer;
- the complete path remains fixed-shape and GPU-native;
- authenticated founders, matched manifests, candidate validation, archive
  lineages, finalist freezing, and sealed evaluation work;
- Shinka produced valid descendant programs under the bounded ABI.

Those are durable contributions and must not be rewritten.

### 2.2 Why r3 did not show recursive improvement

R3 was a valid negative result, not a broken implementation. It exposed two
scientific design failures:

1. The selected tail-actuator injury helped the clone on the sealed panel. The
   clone’s shocked-minus-sham effect was positive, so the event was not a valid
   catastrophe for the central recovery claim.
2. Shinka returned four scores that trusted code resolved with deterministic
   `argmax` among clone, parametric, structural, and mixed mutation. The
   mutation rates and magnitudes themselves were fixed. The candidate saw
   ecological summaries but no history of whether each operator’s offspring
   succeeded. The punctuated finalist therefore collapsed to 100% standard
   parametric mutation and did not reliably beat that fixed baseline.

R3 consequently tested contextual switching among four human-written choices.
It did not yet test online adaptive operator selection with credit assignment,
nor did it give Shinka meaningful mutation-scale choices.

### 2.3 The exact r4 hypothesis

The preregistered hypothesis is:

> Under a sequential healthy-to-costly environment, a Shinka-evolved scheduler
> using recent offspring credit and multiple trusted mutation scales will
> improve sealed post-shock recovery relative to its own initial fixed
> scheduler, without materially degrading sham performance.

The primary comparison is intentionally descendant versus ancestor:

```text
selected punctuated Shinka descendant
minus
the exact r4 initial program from which Shinka began
```

That is the cleanest evidence that the recursive program lineage produced an
improvement. Comparisons with fixed operators, a human adaptive scheduler,
stable-trained Shinka, and the matched-budget structured-random control remain
important but are secondary.

## 6. Research basis for the design

The design follows the current evidence rather than adding arbitrary features:

- ShinkaEvolve is strongest when an LLM edits one bounded executable program
  that receives objective verification, while archives and islands retain
  stepping stones. See the [official repository](https://github.com/SakanaAI/ShinkaEvolve),
  [project overview](https://sakana.ai/shinka-evolve/), and
  [paper](https://arxiv.org/abs/2509.19349).
- Adaptive operator selection separates credit assignment from action
  selection; recent credit is especially relevant in nonstationary settings.
  See [Fialho et al. 2010](https://doi.org/10.1007/s10472-010-9213-y).
- Automatically designed adaptive mutation operators can benefit from
  historical signals rather than static rules. See
  [Hong et al. 2021](https://link.springer.com/article/10.1007/s40747-021-00507-6).
- Mutation scale and correlated variation matter, but full covariance
  adaptation is unnecessary for this proof of concept. See
  [Hansen and Ostermeier](https://doi.org/10.1162/106365601750190398) and
  [Vassiliades and Mouret](https://arxiv.org/abs/1804.03906).
- Stress-linked exploration can help in some ecologies but should be discovered,
  not assumed. See [Ram and Hadany](https://pubmed.ncbi.nlm.nih.gov/22759304/)
  and [Wei et al.](https://www.nature.com/articles/s41467-022-32353-6).
- Sequential environmental transitions can differ from averages over static
  environments, supporting complete pre-shock-to-recovery episodes. See
  [Abreu et al. 2024](https://www.nature.com/articles/s41559-024-02475-9).
- Changing pressure can produce distinct strategies, motivating the matched
  stable-versus-punctuated treatment. See Sakana’s
  [Digital Red Queen](https://pub.sakana.ai/drq/).
- Few-run stochastic comparisons need paired effects, interval estimates, IQM,
  and probability of improvement rather than isolated point estimates. See
  [Agarwal et al. 2021](https://proceedings.neurips.cc/paper/2021/hash/f514cec81cb148559cf475e7426eed5e-Abstract.html).

These sources motivate the bounded design. They do not make any positive r4
result inevitable.

## 7. System architecture

### 7.1 Unchanged inner ecosystem

Each world continues to contain:

```text
32 fixed organism slots
8 living organisms initially
8 nodes and 6 actuated hinges per filament
one padded 15-node / 30-connection TensorNEAT CPPN per slot
one finite shared resource field
food-earned asynchronous reproduction
energy-based death and immediate slot reuse
individual IDs, parent IDs, generations, and founder-lineage IDs
```

All initial organisms in one episode carry copies of one authenticated founder
CPPN. No founder organism is protected or kept alive artificially. “Clonal
start” only means that competing heredity policies begin from the same genotype
within a world, so post-start genetic differences are caused by reproduction.
Generalization comes from using multiple independently authenticated founder
genotypes across worlds.

This controlled start is retained because it:

- isolates the effect of heredity policy from initial population mixture;
- enables exact clone and ancestor comparisons;
- makes genetic divergence and common-garden adaptation interpretable;
- does not prevent diversity from emerging after the first birth.

### 7.2 Accelerator boundary

All r4 additions must remain fixed-shape JAX PyTrees:

- one scalar actuation-cost multiplier;
- fixed per-slot operator provenance arrays;
- fixed six-element operator-credit arrays;
- a six-logit candidate output;
- categorical selection with a JAX key;
- the existing padded TensorNEAT mutation and cached CPPN inference.

There may be no Python callback inside a physics step or birth path, no dynamic
array resizing, and no per-candidate physics recompilation.

The system remains GPU-native but not fully differentiable. CPPN inference and
continuous mechanics remain differentiable between discrete transitions;
birth, death, resource clipping, categorical selection, structural mutation,
and catastrophes are intentionally discrete. R4 makes no end-to-end gradient
claim.

### 7.3 Trusted-versus-evolvable boundary

```text
Trusted and immutable during search       Evolvable by Shinka
--------------------------------------     -------------------------------
Microcosmos mechanics                      body of make_offspring only
resource and metabolic accounting          arithmetic on supplied arrays
founder artifacts and manifests            six bounded output logits
all six mutation implementations
operator outcome credit assignment
random-key splitting and action sampling
birth, death, lineage, and slot reuse
shock schedule and cost multiplier
metrics, score, validation, and budgets
development and sealed partitions
```

The candidate proposes a selection law. It never receives or returns a genome
and never implements mutation directly.

## 8. R4 heredity action space

### 8.1 Six trusted actions

Use these exact indices everywhere:

| Index | Name | Meaning |
|---:|---|---|
| 0 | clone | Exact parent CPPN |
| 1 | parametric-conservative | Half the current standard value-mutation probability and magnitude |
| 2 | parametric-standard | The current r3 parametric mutation |
| 3 | parametric-exploratory | Twice the standard value-mutation probability and magnitude, within existing gene bounds |
| 4 | structural | The current r3 structure-only mutation |
| 5 | mixed | The current r3 standard value-plus-structure mutation |

The predeclared parametric profiles are:

| Parameter | Conservative | Standard | Exploratory |
|---|---:|---:|---:|
| value mutation rate | 0.10 | 0.20 | 0.40 |
| value mutation power | 0.075 | 0.15 | 0.30 |
| value replacement rate | 0.0075 | 0.015 | 0.030 |
| activation replacement rate | 0.05 | 0.10 | 0.20 |

Structural and mixed rates remain exactly as in r3:

```text
connection add/delete rate: 0.20
node add/delete rate:       0.10
```

Do not tune these six profiles after the disturbance screen or after viewing
Shinka outcomes. If the opportunity assay fails, create a new prospective r4b
run rather than silently changing them.

### 8.2 Minimal core implementation

Extend `src/microcosmos/cppn.py` so `build_tensorneat_genome` accepts an
immutable profile specification. Preconstruct the three parametric kernels and
the existing structural and mixed kernels at import time. Every kernel uses the
same padded genome shape and existing bounds.

Preserve the r3 four-score `mutate_cppn` entry point and its baseline policies
for regression and replay. Add a versioned r4 entry point, implemented from the
same private trusted primitives, that separates:

```python
select_operator(logits, selection_key) -> operator_index
apply_operator(parent, operator_index, mutation_key, child_id) -> child
```

Trusted code splits the existing identity-stable mutation key:

```python
selection_key, mutation_key = jax.random.split(context.key)
```

The candidate cannot inspect either key. Fixed baselines bypass categorical
selection and call their exact operator index, which preserves exact accounting
and avoids accidental stochasticity in fixed controls.

This is one heredity implementation with two small versioned adapters, not two
mutation frameworks. The run spec chooses the contract statically before JIT.

Candidate logits are converted to `float32`, required to have shape `(6,)`,
required to be finite, clipped to `[-8, 8]`, and sampled with
`jax.random.categorical`. Invalid output fails closed to clone, increments the
policy-violation counter, and invalidates the episode for candidate scoring.

There is one trusted exact-selection rule: if one clipped logit is exactly `8`
and all other clipped logits are exactly `-8`, choose the unique maximum
without sampling. This rule applies to every candidate, not to a privileged
source hash. It makes the saturated r4 initial program and fixed-choice
descendants genuinely exact while preserving probabilistic mixtures for all
other logits.

## 9. Operator credit: the minimal feedback loop

### 9.1 Why credit is the key RSI addition

Population decline can indicate stress, but it does not tell a scheduler which
kind of mutation produced viable descendants. R4 adds recent, trusted outcome
history so the evolved program can improve future heredity decisions using
results created by its earlier decisions.

The recursion remains bounded:

```text
scheduler chooses operator
        ↓
operator creates child
        ↓
child succeeds or fails in the ecosystem
        ↓
trusted code updates recent operator credit
        ↓
scheduler sees credit before a later birth
```

### 9.2 Fixed-shape state additions

Add to `PopulationState`:

```python
birth_operator:      int32[capacity]   # -1 for founders/inactive slots
birth_step:          int32[capacity]
has_reproduced:      bool[capacity]
operator_success_ema: float32[6]
operator_usage_ema:   float32[6]
operator_evidence_ema: float32[6]
birth_rate_ema:      float32 scalar
death_rate_ema:      float32 scalar
```

Do not add a variable event buffer or Python-side online state.

### 9.3 Credit event definition

Founders are excluded because no r4 operator created them.

For a child created by operator `k`:

1. Record `birth_operator=k`, `birth_step=current_step`, and
   `has_reproduced=False`.
2. When that organism reproduces for the first time, resolve one success:

   ```text
   outcome = exp(-time_to_first_reproduction / credit_time_scale)
   ```

   This is bounded in `(0, 1]` and gives more credit to earlier reproduction.
3. If it dies before first reproduction, resolve `outcome=0`.
4. Resolve an organism at most once. Repeated reproduction cannot repeatedly
   reward the same birth operator.
5. Aggregate all resolutions for each operator within the physics step and
   update that operator once, independent of slot order.
6. Aggregate all birth actions within the step and update usage once per
   operator.

Freeze:

```text
credit_time_scale = maturity_age + 2 * chunk_steps
outcome EMA alpha  = 0.10
usage EMA alpha    = 0.05
evidence EMA alpha = 0.10
```

If implementation profiling shows these units are inconsistent, correct them
before the r4 preregistration is hashed; never change them after the
qualification screen begins.

Initialize success to `0.5`, usage to `0`, and evidence to `0`. Evidence tells
the policy that an apparently neutral success value is untested rather than
earned.

For `n_k` same-step outcomes of operator `k`, let `m_k` be their mean and use:

```text
w_k = 1 - (1 - outcome_alpha) ** n_k
success_ema[k] = (1 - w_k) * success_ema[k] + w_k * m_k
```

Use the same count-weighted form for evidence and usage. Freeze lifecycle order
as: identify first-reproduction and death resolutions, update batched credit,
then create births and register each new child’s provenance. A parent’s first
reproduction is therefore credited before its newly created child is recorded.

### 9.4 Credit invariants

Tests must prove:

- founders never update operator credit;
- an offspring receives the exact operator used at its birth;
- a successful child resolves credit once at first reproduction;
- a death-before-reproduction resolves exactly one zero outcome;
- slot reuse clears old provenance before creating a new child;
- simultaneous births and deaths update fixed arrays without order leakage;
- operator usage sums to one action per valid birth;
- no outcome from one world or episode leaks into another reset;
- disabled or unseen operators remain finite and evidence-weighted;
- credit updates are identical on CPU and GPU within numerical tolerance.

## 10. Candidate ABI

### 10.1 Evolvable function

Create a new r4 initial source rather than overwriting the r3 source:

```python
# examples/evo2_ecosystem/initial_r4.py

# EVOLVE-BLOCK-START
def make_offspring(
    parent_genome_summary,
    parent_stats,
    population_stats,
    operator_stats,
    rng,
):
    """Return six trusted-operator logits; do not mutate a genome."""
    del parent_genome_summary, parent_stats, population_stats, operator_stats, rng
    return jnp.array([-8.0, -8.0, 8.0, -8.0, -8.0, -8.0])
# EVOLVE-BLOCK-END
```

This initial ancestor is the r3 punctuated finalist lifted into the r4 action
space: always choose standard parametric mutation. Both stable and punctuated
outer searches start from the exact same source hash.

The `rng` parameter remains only for compatibility with the existing evaluator
contract. AST validation forbids reading it; trusted code owns sampling.

### 10.2 Candidate inputs

Expose only normalized, bounded arrays with documented index constants.

`parent_genome_summary`, shape `(2,)`:

```text
[active_node_fraction, active_connection_fraction]
```

`parent_stats`, shape `(3,)`:

```text
[energy_fraction, intake_ema, age_fraction]
```

`population_stats`, shape `(6,)`:

```text
[
  alive_fraction,
  mean_energy_fraction,
  population_change_ema,
  birth_rate_ema,
  death_rate_ema,
  mean_intake_ema,
]
```

R4 deliberately omits online genome diversity. Population, energy, intake,
births, deaths, and operator outcomes already give the scheduler bounded
ecological context, while a genome-distance statistic would add per-step work
and another design choice. Genome diversity remains an offline diagnostic
computed from saved finalist genomes.

`operator_stats`, shape `(3, 6)`:

```text
row 0: recent success EMA
row 1: recent usage EMA
row 2: recent evidence EMA
```

All inputs are clipped to `[0, 1]` except signed population change, which is
clipped to `[-1, 1]`.

Remove r3 `lineage_entropy` and `action_diversity` from the r4 candidate view.
A clonal initial founder makes founder-lineage entropy structurally
uninformative, and action diversity is partly an output of the scheduler itself.
They remain available as diagnostics, not decision inputs or rewards.

### 10.3 Information the candidate never receives

- event type, event time, or cost multiplier;
- train/development/sealed identity;
- stable-versus-punctuated arm identity;
- world, founder, or numerical-repeat seed;
- future catastrophe schedule;
- absolute simulation step;
- hidden metrics or baseline scores;
- raw genome tensors, node positions, fields, or simulator objects;
- file, network, subprocess, reflection, imports, or environment variables;
- a usable random key.

The scheduler must infer ecological change from legitimate state and outcome
history.

### 10.4 Validator

Extend the current AST validator; do not create a second sandbox.

Allowed:

- local scalar/array arithmetic;
- `jnp` operations from the existing allowlist;
- indexing and reductions on supplied arrays;
- fixed control flow that traces under JAX.

Forbidden:

- imports, I/O, network, subprocess, reflection, globals, mutation of inputs;
- shape creation dependent on data;
- inspection or use of `rng`;
- dynamic compilation or callbacks;
- non-finite or wrong-shape output;
- candidate runtime above the fixed microbenchmark budget.

Validate source before any ecosystem rollout, then trace and execute a tiny
synthetic panel covering all input extremes.

## 11. The r4 disturbance

### 11.1 Primary event: global actuation-cost increase

Add `actuation_cost_multiplier: float32 scalar` to `EcosystemState`.

At reset:

```text
actuation_cost_multiplier = 1.0
```

At the event boundary, the shock branch assigns a persistent value greater
than one. The sham branch leaves it at one.

Energy accounting becomes:

```text
actuation_energy =
    existing_actuation_energy(intended_action)
    * actuation_cost_multiplier
```

Physical actuation remains unchanged. This avoids the r3 injury confound where
removing an actuator could improve locomotion or reduce useful effort. The same
requested gait now costs more, and descendants can adapt only by finding a
more efficient or productive controller.

The candidate does not receive the multiplier directly.

### 11.2 Why viscosity is not the primary event

A viscosity switch is physically interesting but requires switching solver
configuration or precompiled rollout kernels and creates a larger
interpretation surface. The cost multiplier is one ecological scalar in the
existing energy equation, requires no new physics, preserves fixed shapes, and
directly tests adaptation of controller heredity. Viscosity remains a later
transfer family only if separately qualified.

### 11.3 Prospective disturbance grid

Before any Shinka call, screen in this fixed order:

```text
1.25, 1.50, 2.00, 3.00
```

Select the first, weakest multiplier passing every qualification criterion.
This avoids choosing the multiplier with the most favorable mutation-policy
result.

If no multiplier passes, stop r4. Do not fall back to the r3 injury or tune the
score. A new disturbance family requires a new preregistered run ID.

## 12. Qualification before outer search

Qualification uses training-only founders and world seeds. Development and
sealed artifacts remain inaccessible. This is benchmark construction, not a
positive-result analysis.

### 12.1 Founder eligibility check

Do not use the vague phrase “founder gate.” The check has one explicit purpose:
ensure each initial CPPN can support a healthy pre-event lifecycle before it is
used to test recovery.

Build a new r4 bank with disjoint prepartitioned candidate ranges:

```text
training:    4 founders
development: 4 founders
sealed:      8 founders
```

Within each range, select the first candidates in ascending index order that,
under clone heredity and no shock, satisfy all of:

```text
alive at event boundary >= 2
cumulative births before event >= 2
maximum generation before event >= 1
mean pre-event productivity >= 0.01
all numeric, identity, graph, resource, and energy invariants valid
```

This check never examines post-shock fitness and never keeps a founder alive.
It prevents an unviable starting controller or unlucky world from making the
catastrophe uninterpretable.

Founder candidate ranges and world-seed ranges are fixed in the preregistration
before screening. If a partition cannot be filled, stop and issue a new run ID;
do not borrow candidates from another partition.

### 12.2 Harm criterion

For each candidate multiplier, run matched clone shock/sham pairs sharing one
exact pre-event trajectory. Define:

```text
clone_effect = shock absolute post-event AUC - sham absolute post-event AUC
```

The multiplier passes harm only if:

```text
mean clone_effect <= -0.03
and founder-first paired-bootstrap 95% upper bound < 0
```

The negative sign is mandatory. This is the direct repair for r3.

### 12.3 Recovery remains possible

The same multiplier must leave a viable evolutionary problem:

```text
clone or standard-parametric survival fraction >= 0.75
median post-shock births >= 4
median post-shock generation gain >= 1
at least one non-clone profile creates a genetically distinct child
at least one distinct child survives to maturity or first reproduction
all integrity checks pass
```

Do not require a conventional policy to beat clone. That would select the
benchmark for the desired result. Require only harm, ongoing reproduction, and
available heritable variation.

### 12.4 Contextual operator-opportunity assay

Before spending the Shinka budget, prove that scheduling can help within the
six-action ABI.

1. Collect a fixed pool of valid imminent-birth states from pre-shock and
   post-shock training episodes.
2. For each state and action, use eight preregistered mutation keys rather than
   one lucky draw.
3. Force children through the trusted action and evaluate them in identical
   short post-shock common gardens.
4. Measure survival, intake, energy retained, and time to first reproduction;
   average repeated draws within state and action.
5. Retain the per-state contextual oracle only as a descriptive ceiling.
6. Run leave-one-founder-out cross-fitting of a deliberately small scheduler
   that uses the actual r4 ABI: enumerate one input feature, one threshold from
   the fixed grid `0.1, ..., 0.9`, and one trusted action below and above the
   threshold. Fit the choice on three founders and evaluate it on the unseen
   fourth founder.
7. Compare cross-fitted out-of-founder performance with the best single fixed
   action selected only on each training fold.

The action space is qualified only if:

```text
cross-fitted scheduler mean advantage >= 0.03 normalized score
paired 95% lower bound > 0
the selected threshold rules use at least two distinct non-clone actions
each action has >= 8 resolved outcomes before and after shock across the assay
```

This prevents the maximum of six noisy counterfactual draws from qualifying the
benchmark. If the out-of-founder scheduler cannot beat one fixed action, no
learnable scheduling advantage has been demonstrated. Change the action
profiles or disturbance only under a new prospective run ID.

Neither the oracle nor the fitted threshold scheduler becomes a main-result
baseline. They are pre-search feasibility checks; the independently written
human credit scheduler remains the main adaptive baseline.

### 12.5 Sufficient resolved credit

Across the training-only qualification panel require:

```text
at least 24 resolved non-founder outcomes before shock
at least 24 resolved non-founder outcomes after shock
at least two non-clone operators with evidence EMA >= 0.10 in each period
```

Births without resolved offspring outcomes are not enough. If the horizon is
too short for credit to update, the proposed feedback loop cannot be evaluated.
Change the horizon only before manifests and the r4 preregistration are frozen.

### 12.6 Observable-but-not-labeled stress

Confirm that at least one legitimate candidate input changes after shock:

```text
population or intake feature standardized mean difference >= 0.5
or operator-credit distribution total variation >= 0.20
```

This confirms that a scheduler can infer a changed ecology without receiving a
scenario label.

## 13. Episode and manifest design

### 13.1 Complete sequential episodes

Every episode contains:

```text
healthy pre-event prefix
event boundary
sham or cost-shock continuation
fixed post-event recovery horizon
```

Do not average separate static healthy and costly worlds. The population and
operator-credit state must flow through the transition.

### 13.2 Exact shock/sham pairing

For every `pair_id`:

1. Run one pre-event prefix.
2. Freeze the complete state at the event boundary.
3. Fork the state into sham and shock branches.
4. Use identical step- and identity-derived post-event random streams in both
   branches. Do not include a branch label. The deterministic cost event is the
   only initial difference; later RNG divergence may arise only from causal
   state and identity divergence.

This prevents pre-event ecological drift from masquerading as a shock effect.

### 13.3 Partition sizes

Preregister:

```text
training:     8 pairs over 4 founders and 2 independent contexts per founder
development:  8 pairs over 4 unseen founders
sealed:       16 pairs over 8 unseen founders
```

Use disjoint founder, world, event-time, spawn, mutation, and analysis seed
ranges. The sealed suite also uses unseen event times. Its primary test keeps
the qualified training cost multiplier fixed; any secondary magnitude-transfer
panel follows the mapping frozen in section 19.1.

### 13.4 Stable-versus-punctuated outer treatment

Both outer arms execute the same number of episodes and simulator steps.

- Stable arm archive score and proposer feedback use only sham continuations.
- Punctuated arm archive score uses a balanced combination of each matched sham
  and shock continuation.
- Shock metrics executed for the stable arm remain private and inaccessible
  until both archives are closed. Candidate programs are stateless between
  episodes, so merely executing those episodes cannot train them.

This gives equal compute while changing only outer selection pressure.

## 14. Metrics and scoring

### 14.1 Absolute productivity is the scored quantity

Use the existing r3 absolute-productivity definition, normalized by one frozen
world resource-supply reference that is identical for every policy. For
post-event chunk `t`:

```text
gross_productivity_t = cumulative_intake_t / (chunk_steps * dt)
resource_reference = sum(post_event_resource_regeneration_map)
A_t = clip(gross_productivity_t / resource_reference, 0, 1)
```

The scored post-event AUC is the mean of `A_t` over the fixed horizon. It cannot
be inflated by deliberately lowering the candidate’s own pre-shock behavior.

For diagnostic recovery curves only, let `P_pre` be mean population intake
during the fixed pre-event window and show:

```text
R_t = clip(P_t / (P_pre + epsilon), 0, 1.5)
```

Do not optimize or use the candidate-relative `R_t` curve in qualification,
search, selection, or the primary effect.

Also record:

- time to sustain 80% of pre-event productivity for three chunks;
- survival through the horizon;
- post-event births and deaths;
- maximum generation and generation gain;
- final productivity and population energy;
- operator usage, credit, evidence, and action transitions;
- parent–child CPPN distance and graph validity.

### 14.2 Balanced punctuated search score

For each pair, use the harmonic mean of nonnegative sham and shock absolute
post-event AUC:

```text
balanced_pair =
    2 * sham_absolute_auc * shock_absolute_auc
    / (sham_absolute_auc + shock_absolute_auc + epsilon)
```

This prevents a policy from improving its apparent shock ratio by deliberately
lowering healthy performance. Survival and integrity are hard gates, not
additive bonuses.

### 14.3 Direct recursive-improvement score

Cache the exact r4 initial ancestor’s results on every training pair and
numerical repeat. Candidate pair delta is:

```text
candidate balanced_pair - initial balanced_pair
```

For repeat `r`, evaluate the candidate and cached ancestor with the same
founder/world keys and compute pair deltas before any repeat selection. The
punctuated scalar returned to Shinka is:

```text
0.8 * IQM(candidate pair deltas)
+ 0.2 * lower-quartile mean(candidate pair deltas)
```

The stable scalar uses the same formula on sham-only AUC deltas.

Subtracting the cached ancestor does not change rankings when all evaluations
are perfectly paired, but it makes the recursive-improvement target explicit,
reduces shared-world noise, and gives the proposer useful causal feedback.

### 14.4 No diversity reward

Do not optimize lineage entropy, genome diversity, or action diversity
directly. They are mechanistic diagnostics. A policy must not receive reward
for maintaining useless diversity or taking a second action solely to appear
adaptive.

### 14.5 Hard invalidity

An episode or candidate is invalid if any of these occur:

- candidate source or output validation fails;
- any policy violation occurs;
- wrong operator accounting occurs;
- NaN, Inf, invalid graph, identity collision, negative resource, or energy
  creation occurs;
- population starts from the wrong authenticated founder;
- event or manifest hash mismatches;
- simulator-call or wall-time budget is exceeded;
- complete matched results are missing.

Invalid candidates receive a fixed score below every valid candidate and
diagnostic feedback describing only the public failure.

## 15. Numerical reproducibility

The existing GPU implementation is not bitwise deterministic because of XLA
scatter/reduction behavior. R4 must not treat GPU reruns as ecological
replicates.

Before freezing the r4 run spec, run one focused smoke test with OpenXLA’s
documented deterministic exclusion flag:

```text
--xla_gpu_exclude_nondeterministic_ops
```

Use it only if the complete focused episode succeeds and runtime is no more
than twice ordinary execution. R3 already found strict deterministic execution
impractically slow; failure or excessive cost is an expected outcome, not a
reason to redesign the project.

Otherwise:

```text
outer search and development: 3 complete-manifest numerical executions
sealed selected policies:     5 complete-manifest numerical executions
```

For the scalar evaluator, select the coherent complete-manifest repeat whose
aggregate **paired candidate-minus-ancestor delta** is the median, with stable
tie breaking. Never select independent candidate and ancestor medians, and
never form a synthetic result by taking a favorable median independently for
each world or metric.

For final inference, compute paired effects within repeat index, then aggregate
across repeats. Bootstrap founder first and paired worlds within founder.
Report repeat ranges separately. Numerical repeats are uncertainty probes, not
independent sample-size inflation.

Verify empirically during qualification that shock/sham pairing reduces effect
variance. If it increases variance, retain exact pairs for causal consistency
but do not claim variance reduction.

## 16. Outer search

### 16.1 Budget

Each arm receives exactly:

```text
1 evaluated initial ancestor
50 LLM-generated descendant programs
2 islands
archive capacity 32
identical ecosystem manifests, repeats, timeouts, and simulator-call limits
```

Use “50 LLM-generated descendants plus one initial program” in reports. Do not
confuse Shinka generation counters with the number of LLM-created proposals.

R3’s fourteen generated descendants were a smoke-sized search. Fifty is a
meaningful final attempt while remaining bounded and far smaller than an
unrestricted code-evolution run.

### 16.2 Search ancestry

Both arms begin from the lifted r3 punctuated program that always chooses
standard parametric mutation. The exact initial source and hash are frozen.

Shinka may discover:

- probability matching from recent success;
- exploration of low-evidence operators;
- conservative mutation during stability;
- exploratory mutation under decline;
- temporary structural exploration;
- parent- or topology-conditioned choices;
- recovery-sensitive decay back toward conservative mutation.

Shinka cannot change mutation kernels or add actions.

### 16.3 Search feedback

Return only training-visible diagnostics:

- combined paired delta score;
- sham and shock absolute-AUC deltas for the punctuated arm;
- births, deaths, survival, and generation gain;
- pre-event and post-event action fractions;
- success, usage, and evidence EMA summaries;
- parent–child graph and magnitude summaries;
- invalidity and runtime flags;
- concise textual diagnosis of the largest weakness.

Stable-arm feedback must omit shock outcomes. Neither arm sees development or
sealed outcomes.

### 16.4 Multi-fidelity rule

Default to one uniform training fidelity. Do not add successive halving merely
to save time.

Multi-fidelity screening is allowed only if a preregistered pilot of at least
12 fixed or hand-written policies finds Spearman rank correlation `>= 0.70`
between cheap and full development scores. If that gate passes, all Shinka
candidates receive the cheap panel and archived finalists receive full
development reevaluation. If it fails, use uniform fidelity and reduce no
candidate’s budget opportunistically.

### 16.5 Equal-budget random control

Random search receives the same 50 candidate evaluations and training
manifests. Randomly sample a frozen linear/threshold scheduler grammar over the
same candidate inputs and six logits. It may not sample arbitrary Python or
mutation kernels. Call this the **matched-budget structured-random baseline**.
It tests a simpler non-LLM search control but does not occupy the complete
bounded arithmetic-program space available to Shinka; conclusions must retain
that limitation.

## 17. Baselines

Evaluate these exact systems through the same trusted action kernel:

1. exact clone;
2. fixed conservative parametric;
3. fixed standard parametric;
4. fixed exploratory parametric;
5. fixed structural;
6. fixed mixed;
7. lifted r3 / r4 initial ancestor;
8. frozen human stress-responsive scheduler;
9. frozen human credit-responsive probability-matching or UCB scheduler;
10. matched-budget structured-random scheduler champion;
11. selected stable-trained Shinka descendant;
12. selected punctuated-trained Shinka descendant.

The human credit baseline must be written and frozen before any Shinka result is
viewed. It should combine recent success with an evidence-dependent exploration
bonus and use the same logits and trusted sampler. Do not tune it on sealed data.

## 18. Development selection and finalist freezing

After both archives close:

1. Authenticate the complete stable and punctuated archives.
2. Restore development permissions; sealed remains mode `000`.
3. Select the top five training candidates per arm by the frozen archive score,
   preserving distinct source hashes.
4. Evaluate each top-five candidate on the full development panel.
5. Always choose and freeze the highest-scoring valid unrestricted candidate.
6. If any candidate satisfies the adaptive eligibility rule below, also choose
   the highest-scoring adaptive-eligible candidate. It becomes the
   mechanism-primary finalist; the unrestricted champion is a secondary
   performance finalist if distinct.
7. If no candidate is adaptive eligible, the unrestricted champion becomes the
   preregistered performance-only primary finalist and still receives the
   sealed descendant-versus-ancestor test.
8. Freeze source, full parent chain, archive lineage, run spec, manifests,
   hashes, development results, finalist type, and selection record.

### 18.1 Adaptive eligibility is a classification, not a reward

A candidate may be called “adaptive” only if:

```text
at least two non-clone actions each have mean trusted selection probability
>= 5% across births
and
pre-event versus post-event expected action-probability distributions have
total variation >= 0.20 with a founder/repeat bootstrap interval excluding the
fixed-mixture null
```

It must also remain valid and survive the development panel.

Do not add these thresholds to the optimization score. If no candidate meets
them, the adaptive claim fails, but the unrestricted performance-only test
remains valid. If that champion is behaviorally one fixed action, any positive
result is baseline rediscovery rather than an adaptive heredity mechanism.

Record candidate logits or trusted softmax probabilities at each birth for
this classification. Realized action counts remain diagnostic; they cannot by
themselves establish adaptiveness because categorical sampling can create
apparent pre/post differences.

Do not store an unbounded birth history during search. Trusted chunk telemetry
accumulates `selection_probability_sum[6]` and `selection_probability_count`
before and after the event; each episode returns only those fixed summaries.
Finalist replay may include per-birth probabilities in the host-side lineage
ledger.

## 19. Sealed examination

### 19.1 Sealed suite

After all sources, selection records, metrics, and analysis code are frozen,
unlock the sealed partition once.

The sealed primary family contains:

- 8 unseen founders;
- 16 matched shock/sham pairs;
- unseen world and mutation seeds;
- unseen event timing;
- the same prospectively qualified multiplier used in punctuated training.

Using the same event magnitude keeps the single primary test confirmatory; new
founders, worlds, seeds, and event timing already test generalization. A
secondary in-family transfer panel may use the next larger multiplier in the
frozen grid, but only if that multiplier passed clone-harm and viability checks
on training-only qualification controls before outer search. The transfer
panel cannot replace or redefine the primary result.

Freeze this mapping before qualification:

```text
training 1.25 -> transfer 1.50
training 1.50 -> transfer 2.00
training 2.00 -> transfer 3.00
training 3.00 -> no magnitude-transfer panel
```

Use a disjoint, predeclared training-only qualification-control seed range for
the mapped transfer value. Never use development or sealed founders to choose
or qualify it.

An optional transfer family such as resource relocation may be included only
if it was separately qualified and frozen before outer search. Failure on a
different family does not invalidate the primary result; it limits transfer.

Do not introduce a post-hoc viscosity or injury test after seeing primary
results.

### 19.2 Primary effect

For every sealed pair:

```text
primary_delta =
    punctuated_shinka_shocked_absolute_auc
    - r4_initial_shocked_absolute_auc
```

The balanced harmonic score is an outer-search objective, not the sealed
primary claim. Sham noninferiority is a hard gate. Report shock-minus-sham
difference-in-differences as secondary causal evidence.

Aggregate with a founder-stratified paired bootstrap and report:

- mean and median paired effect;
- 95% interval;
- interquartile mean and interval;
- probability of improvement;
- per-founder effect plot;
- complete recovery curves.

### 19.3 Secondary effects

Report, without redefining success:

```text
punctuated Shinka - stable Shinka
punctuated Shinka - best fixed trusted action
punctuated Shinka - human stress scheduler
punctuated Shinka - human credit scheduler
punctuated Shinka - matched-budget structured-random champion
```

Correctly label all multiple secondary comparisons as exploratory or apply a
predeclared family correction. The primary descendant-versus-ancestor contrast
is singular.

### 19.4 Stable-performance safeguard

The selected punctuated descendant must not buy recovery by collapsing healthy
performance. Use a preregistered noninferiority margin:

```text
95% lower bound of sham absolute-AUC delta versus initial > -0.02
```

## 20. Proving heritable adaptation

### 20.1 Sparse genome capture

Only for frozen finalists and baselines, replay sealed episodes with sparse
snapshots enabled. Capture:

- representative genomes immediately before shock;
- candidate descendants near the end of recovery.

The current compact rollout does not retain a complete multi-generation
ancestry after intermediate parents die and slots are reused. Add a
**finalist-only host-side lineage ledger** to replay. At each chunk boundary,
export fixed birth-event rows containing:

```text
child individual ID
parent individual ID
birth operator
birth step
child CPPN genome hash
child CPPN genome payload for selected replay artifacts
```

Append those compact rows in Python after device synchronization and reconstruct
the exact ancestry path before selecting a lineage-matched pair. This ledger is
disabled during search and ordinary evaluation, so it adds no per-candidate
memory burden and cannot affect selection.

Do not retain full trajectories during search.

### 20.2 Common-garden assay

For each lineage-matched ancestor/descendant pair:

1. Instantiate the CPPN as a single organism or fixed small clone group.
2. Use the same post-shock cost multiplier, resource field, orientation, and
   random panel for ancestor and descendant.
3. Disable reproduction during the short assay so the tested genotype cannot
   be replaced.
4. Measure resource intake, energy retained, survival, and locomotor efficiency.

Post-shock descendants must outperform their own pre-shock ancestors to support
heritable adaptation. Population recovery alone supports resilience but not
new adaptation.

## 21. Mechanism ablations

Apply these trusted wrapper ablations to the frozen punctuated finalist without
editing its source:

1. **No credit:** replace operator success, usage, and evidence inputs with
   reset values throughout the episode.
2. **Dominant fixed action:** force the finalist’s most-used action at every
   birth.
3. **No exploratory scale:** redirect exploratory-parametric choices to
   standard parametric.
4. **No context transition:** evaluate the same policy on sham episodes.

The discovered mechanism is supported if removing its key adaptive input or
choice materially reduces the sealed advantage. If the no-credit or
dominant-action ablation performs equally, the performance claim may remain but
the credit-adaptive mechanism claim fails.

## 22. Success, partial success, and stop rules

### 22.1 Full bounded-RSI success

Claim bounded recursive improvement only if all hold:

1. The sealed clone shock-minus-sham interval is strictly negative.
2. The punctuated Shinka descendant’s primary mean improvement over its initial
   ancestor is at least `+0.02` absolute post-event AUC.
3. The founder-first 95% lower bound of that primary effect is greater than
   zero.
4. Sham performance satisfies the `-0.02` noninferiority margin.
5. The candidate satisfies adaptive eligibility and is not equivalent to one
   fixed action.
6. Its action or mutation-scale distribution changes across ecological
   contexts.
7. Post-shock descendants beat matched ancestors in common garden with a
   positive interval.
8. Removing the discovered credit or scheduling mechanism removes at least
   half of the primary gain or yields a positive finalist-versus-ablation
   interval.

### 22.2 Performance-only success

If criteria 1–4 hold but the policy behaves like one fixed action, claim:

> ShinkaEvolve autonomously rediscovered a stronger fixed heredity operator for
> this embodied ecology.

Do not call it adaptive operator selection.

### 22.3 Mechanistic but statistically uncertain result

If behavior is clearly adaptive but the primary interval overlaps zero, report
the mechanism as a hypothesis-generating case study and do not claim improved
sealed recovery.

### 22.4 Negative result

Stop and report truthfully if:

- no disturbance passes harm and viability;
- the founder-cross-fitted observable-input scheduler cannot beat one fixed
  action during qualification;
- no valid Shinka descendant satisfies the preregistered performance criteria,
  and no adaptive descendant supports a mechanistic case study;
- the primary sealed interval overlaps zero;
- common-garden or ablation evidence contradicts the mechanism.

Do not change the metric, multiplier, founders, action profiles, or sealed suite
after a negative result.

## 26. Performance budget

R4 must remain within the existing fixed 64×64 fluid world and 32-slot
population unless qualification profiling proves a smaller search fidelity
preserves rank.

Performance requirements:

- candidate code does not change tensor shapes or trigger per-birth compile;
- the six mutation kernels compile once per process;
- credit adds only `O(capacity + operators)` state and work;
- search stores compact metrics, not full node trajectories;
- sparse genomes and trajectories are captured only for frozen finalists;
- one evaluator worker runs on one guarded GPU process;
- result caching keys include candidate source, simulator, manifest, founder,
  contract, and run-spec hashes;
- compilation time and warm rollout time are reported separately.

## 28. Rollback and failure containment

R4 is isolated on new branches and new versioned artifact roots. Rollback means
checking out the frozen r3 branches or reverting r4 commits; it never means
deleting or rewriting r3 evidence.

If core state changes destabilize r3 regressions:

1. stop before qualification;
2. minimize the change inside existing core owners;
3. retain a legacy contract path selected statically by run spec;
4. do not fork a second ecosystem implementation.

If the disturbance fails:

1. write and commit the qualification stop report;
2. do not run Shinka;
3. retain all negative screening results and hashes;
4. propose a new run ID only after a new prospective plan.

If Shinka search fails or produces fixed-action rediscovery:

1. freeze the archives and result;
2. run no sealed fishing beyond the preregistered examination;
3. report the correct performance-only or negative category;
4. do not expand the simulator to rescue the claim.

## 32. Plain-language summary

R3 proved the ecosystem and Shinka connection work, but it did not prove an
improvement. The “catastrophe” accidentally helped the clone, and Shinka could
only choose one of four coarse mutation buttons without seeing whether each
button’s children succeeded.

R4 fixes exactly those two problems.

First, increase the energy cost of actuation and test the shock on clone
controls before any Shinka run. Use it only if it really hurts, but still leaves
births and evolution possible.

Second, give Shinka six safe buttons: clone, three strengths of ordinary CPPN
mutation, structural mutation, and mixed mutation. Track which button created
each child and whether that child later reproduced. Give Shinka only recent,
bounded summaries of those outcomes. It writes the rule for choosing future
buttons; trusted JAX code still performs every mutation.

Then run two equal Shinka searches from the same r3-derived starting program:
one selected only for healthy worlds, and one selected for both healthy and
shocked worlds. The primary final question is whether the punctuated descendant
beats the exact program it descended from on new founders and unseen shocks.

If it wins, changes actions when ecology changes, produces better descendants,
and loses the gain when its credit mechanism is removed, the project has a
strong bounded-RSI result. If it merely selects one fixed mutation type, call it
automated baseline discovery. If it does not win reliably, preserve and report
the negative result.
